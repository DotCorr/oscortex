  DECISION (one sentence)
  ───────────────────────
  Kernel owns hardware and policy. Flutter owns everything above the kernel —
  window management, shell, and applications — with one hard rule: each runnable
  unit that can crash is its own process.

  Flutter is the PERMANENT userspace UI runtime. Every pixel on screen is rendered
  by the Flutter engine through kernel surfaces. Other engines plug in as Flutter-
  hosted views via platform-channel FFI — never as parallel shells or render paths.

  Out of scope for agents: landing/


  EXECUTION MODEL — HOW CODE ACTUALLY RUNS TODAY (JIT, not AOT)
  ─────────────────────────────────────────────────────────────
  The single most important fact about boot time, RAM use, and input latency:
  OSCortex runs the Flutter engine's JIT (debug) build, NOT AOT (release). Almost
  every "why is it slow / heavy" question bottoms out here.

  WHAT SHIPS in a .osx / kernel_blob.bin:
    Dart source ──(flutter build bundle --debug)──▶ kernel_blob.bin
    kernel_blob.bin is Dart KERNEL BYTECODE (portable IL) — NOT native machine
    code. It is a recipe, not a compiled program.

  WHAT HAPPENS AT RUNTIME (this is "compiling the whole framework to memory"):
    1. The JIT engine maps kernel_blob.bin (bytecode).
    2. The FIRST time any function executes, the engine compiles THAT function
       from bytecode to x86-64 machine code on the fly (lazy JIT).
    3. Drawing even one Material screen executes thousands of framework functions
       (MaterialApp, Theme, Scaffold, RenderObject layout, text shaping, paint).
       So producing the first frame forces the engine to JIT-compile ~the whole
       framework. THAT is what the boot spinner is waiting on.

  WHY IT'S EXPENSIVE:
    • TIME  — warmup = JIT-compiling the framework (tens of seconds, high
              variance on emulated bare metal). There is no precompiled code to
              skip, so it pays the cost on every cold path, every boot.
    • RAM   — JIT keeps THREE things resident per isolate: the compiler, the
              source bytecode, AND the generated machine code — plus the object
              heap. Hundreds of MB per Flutter VM. shell + 1 app = the gigabytes.
    • The KERNEL itself is ~64 MB at runtime. The GBs are entirely Flutter-in-JIT,
              not the OS. (Disk image is fat for a different reason: the engine
              .so + every app blob are baked into the 315 MB kernel binary.)

  THE AOT ALTERNATIVE (the target — currently BLOCKED):
    AOT = `flutter build` precompiles ALL Dart (app + framework) to native code
    ahead of time into libapp.so. The engine just maps & runs it: no compiler in
    RAM, no warmup, a fraction of the heap. Phones do this in <512 MB.
    BLOCKER: the engine binary we have is the JIT engine; feeding it AOT snapshots
    on bare metal dead-ended (it can't deserialize AOT instructions). Until that
    is solved, JIT is the ONLY path that renders. This is THE lever for a truly
    fast + lite OS. (History: MEMORY / "jit-not-aot" notes.)

  SCHEDULING REALITY (why a button can feel dead):
    One cooperative, single-core scheduler. User threads run on the BSP only; the
    other cores (APs) just halt. The Dart UI thread, the raster thread, and the
    embedder all share that ONE core and hand off cooperatively (hand-rolled
    futex/cond). While the UI thread is JIT-compiling or GC-ing, input and frames
    wait behind it. The embedder's frame pump is therefore adaptive — gentle
    during warmup, 60 fps for a short window after input, ~8 fps when idle — so it
    doesn't steal that scarce core (tools/flutter-embedder pump_interval_ns).
    Real parallelism needs an SMP scheduler; an active 2nd core currently breaks
    the single-core sync assumptions.

  BOOT-TIME UX:
    Warmup is unavoidable under JIT, so the KERNEL (not Flutter) draws an animated
    loading spinner directly on the framebuffer from first-framebuffer-up until
    Flutter presents its first real frame (drivers/fb.rs::draw_boot_splash, driven
    by compositor::tick). A Flutter spinner can't cover this window — the engine
    isn't ready yet.

  ONE-LINE MENTAL MODEL:
    Kernel = small + fast. Flutter-in-JIT = heavy + slow. Every perf/RAM problem
    is the JIT engine on one cooperative core; the real fix is AOT + an SMP sched.

  APP LIFECYCLE
  ─────────────
  Dev:     flutter project → tools/oscortex-pack → app.osx
  Install: app_install syscall (runtime, persistent storage — Phase 2)
  Launch:  app_launch → spawn /bin/oscortex-host (new PID) + map app JIT blob
           (kernel_blob.bin bytecode — AOT is the TARGET but is blocked today;
            see "EXECUTION MODEL" below)
  ISO:     kernel + init + engine + shell only — no apps/* bake loop

  On-Demand (new):
  Resolve: shell calls pkg_resolve(name) → kernel checks cache → fetches if
           miss → SHA-256 verifies → loads into registry → returns app_id
  Launch:  same as above — app_launch with the resolved app_id
  Evict:   LRU eviction when cache is full (system apps never evicted)


  BOOT (steady state)
  ───────────────────
  Limine → kernel → /init (supervisor)
       → spawn /bin/oscortex-host (shell mode)
       → Flutter shell renders
  User launch → app_launch → new oscortex-host process (app mode)

  On-demand sequence:
  Limine → kernel → net::init (DHCP) → pkg::init (catalog fetch)
       → /init → shell → catalog shown
  User taps remote app → pkg_resolve → HTTP fetch → verify → cache → launch

  ON-DEMAND PACKAGE DELIVERY
  ──────────────────────────
  Inspired by Google Fuchsia's ephemeral software model. Apps are never
  "installed" in the traditional sense — they are fetched on demand, verified,
  cached in memory, and evicted when space is needed.

  KEY DIFFERENCES FROM TRADITIONAL INSTALL:
  ● No download + install step visible to user
  ● Apps stream from server on first tap, launch from cache on re-tap
  ● System apps are pinned (never evicted); user apps are ephemeral
  ● Cache is bounded (16 slots) with LRU eviction
  ● Every bundle is SHA-256 verified before loading into memory

  SYSCALL SURFACE:
  0x390  pkg_resolve(name_ptr, name_len) → app_id   resolve + fetch if needed
  0x391  pkg_catalog(buf_ptr, buf_len) → count       list available packages
  0x392  pkg_set_server(ip_be, port) → 0             configure server IP
  0x393  pkg_evict(app_id) → 0                       manual eviction

  CATALOG FORMAT (binary, no JSON parsing in kernel):
  [4 bytes: entry_count LE]
  [N × 128-byte PkgManifest entries]

  PkgManifest (128 bytes, repr C packed):
    name:       [u8; 64]   fully qualified package name
    version:    [u8; 16]   semver string
    hash:       [u8; 32]   SHA-256 of the .osx bundle
    size_bytes: u32 LE     bundle size
    flags:      u32 LE     0x01 = system (pinned)
    _reserved:  [u8; 8]

  SYSFS ENDPOINT:
  /sys/pkg/cache → "slots=3/16\npinned=1\nephemeral=2\n"

  HARDWARE (summary — full spec in docs/hardware.txt)
  ───────────────────────────────────────────────────
  Kernel owns devices. Flutter sees only syscalls (surfaces, WM, VFS, net).
  Display today: CPU raster → gpu_submit_strided → compositor → framebuffer.
  No traditional GPU driver required for shell. Each device class (audio,
  touchpad, …) is its own driver; CDP WASM drivers are portable across CPUs.
  Do not map hardware into userspace. Do not add parallel render paths.
