# OSCortex v0.1.4 — x86 app-launch under SMP (the long-open "2nd-engine" blocker is fixed)

## Headline
Launching a bundled app on x86 no longer takes down the OS. Under multi-core (SMP),
a launched app (Files, Web Link, Canvas) now **initialises its own Flutter engine and
renders its full UI on a dedicated application core**, while the shell keeps running on
the boot core. This was the multi-session blocker (every app launch used to crash the
shell's dart:io event handler and freeze the machine).

## How it works
Each launched engine's process group is pinned to its own CPU (**home-core isolation**),
so it runs on separate per-CPU register state and never shares the cooperative-scheduler
context that corrupted a second engine on a single core.

## Requirements (important for testing)
- **This build needs ≥2 CPU cores.** On a real Intel Mac (bare metal) that's automatic.
  In UTM/QEMU, set the VM to **2+ cores** (`-smp 2` or higher).
- On a single core, the multi-core isolation is inert and app-launch falls back to the
  old behaviour (the app crashes) — but the OS now **survives** that crash (see below)
  rather than hanging.

## Stability
- **The OS is crash-proof under SMP**: 0 kernel panics / 0 page-table corruption across
  the headless launch test runs with these fixes. A faulting app is torn down and the
  shell keeps running.
- App launch+render succeeds in the large majority of headless runs. An **intermittent
  first-frame stall** remains (the app or shell occasionally initialises but pumps few
  frames) — it is **non-fatal**: the machine stays alive; relaunch/reboot renders.

## Web Link (browser) — scaffold, not a working browser yet
Honest status: **the browser does not browse real web pages yet.** What ships:
- The **Web Link app launches and renders its chrome** + a placeholder web surface.
- The **end-to-end webview pipeline is proven**: the app-side Dart API
  (`oscortex_webview`: loadUrl/back/forward/reload/title/JS/input/resize over the
  `oscortex/webview` MethodChannel) ↔ the embedder's native webview channel handler ↔
  an OSCortex compositor surface z-stacked beneath the app chrome. A **stub engine**
  currently fills that surface and emits URL/progress/nav events, which validates the
  whole path without a real web engine.
- **Not integrated:** the actual web rendering engine (**Servo**) — this is the
  months-long long pole and is the next major effort. Architecture in
  `docs/browser-architecture.md`.

So: the browser's OS-side plumbing + app shell are done and demonstrable; the web engine
behind it is not.

## SMP-safety fixes under the hood (latent bugs the single-core kernel had hidden)
- Per-CPU page-table lock (a global re-entrancy counter let a 2nd core bypass the lock
  → parallel page-table writes → corruption).
- Fixed a PTABLE↔window-manager ABBA lock-order deadlock.
- Reschedule IPI on spawn so an application core wakes immediately.
- Page-table walks degrade to "not mapped" instead of panicking when crash-recovery has
  freed an address space another core still references.
